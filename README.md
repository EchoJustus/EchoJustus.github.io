# EchoJustus.github.io

The content for <https://echojustus.github.io>. The site is generated by
[clogem-press](https://github.com/EchoJustus/clogem-press) and published by
`.github/workflows/publish.yml` through the GitHub Pages **artifact** flow.

**No built HTML is committed to this repository, ever.** The site ships as an
Actions artifact. If you find a `docs/` or `dist/` directory tracked in git,
something has gone wrong.

```
site.edn                     site configuration — the schema is the generator's config.example.edn
permalinks.edn               generated ledger of permalinks and tombstones; committed, not hand-edited
content/
  index.md                   the home page (home: true)
  01.Notes/01.welcome.md     the numbered knowledge-base tree
  _posts/…                   dated blog posts
assets/                      static files, copied through to /assets/
i18n/                        optional UI-string overrides (see i18n/README.md)
overrides/                   reserved for extra CSS / ejected theme namespaces; not read yet
.github/workflows/publish.yml
```

## Numbered directories and files

Everything under `content/` except `index.md`, `_posts/` and `@pages/` is the
**knowledge-base tree**, and its shape comes from the filenames.

```
content/01.Notes/10.Basics/01.first-steps.md
        └──┬───┘ └───┬───┘ └──────┬───────┘
       category  subcategory    article
```

- **Directories** are `NN.Name`. The number is everything before the *first*
  dot and sets sort order; the title is everything after it and becomes the
  category name. `01.Notes` → category *Notes*.
- **Files** are `NN.title.md`. The number is the leading digits of the first
  dot-segment; the title is **everything after that first segment**, once the
  `.md` and any language suffix are removed. `03.Vue.js.md` is number 3, titled
  `Vue.js`; `05.a.b.c.md` is titled `a.b.c`. Dots in a title survive intact.
- **Leave gaps.** `10.`, `20.`, `30.` lets you insert an article later without
  renumbering the directory.
- **Two siblings may not share a number** unless they are language variants of
  the same article (same number *and* same title). Anything else is a build
  error, not a warning.
- A directory with no number is legal at the top level and sorts after the
  numbered ones; below the top level it is accepted with a warning.
- A file that does not start with a number is **skipped with a warning** — it
  will not appear on the site. That is the usual reason a new page "doesn't
  show up".
- Markdown files placed directly in `content/` are not scanned at all. `index.md`
  is the home page; anything else there is ignored.

### `_posts/`

Dated blog posts, not part of the sidebar tree:

```
content/_posts/2026-09-05-hello-world.md          → category from :content :category-text ("Notes")
content/_posts/notes/2026-09-05-hello-world.md    → category "notes", a different article
```

No numbering. The `YYYY-MM-DD-` prefix is stripped from the displayed title but
is part of the post's identity, so two posts may share a slug on different
dates. Sorting uses the `date:` field in the front matter, not the filename —
write both and keep them in agreement.

### `@pages/`

Reserved for generated index pages. You do not create these by hand — and note
that the current generator does not create them either: `@pages/` is excluded
from the scan, and any file you put there is **silently ignored**, with no
warning. Leave it alone.

## Language suffixes

A translation is a **sibling file with a language-code suffix**, sharing the
number and the title:

```
content/01.Notes/01.welcome.md            English
content/01.Notes/01.welcome.zh-Hans.md    简体中文
content/01.Notes/01.welcome.ta.md         தமிழ்
```

The configured languages are `en`, `zh-Hans`, `zh-Hant`, `ms`, `ta` — the
`:langs :locales` map in `site.edn`. The suffix is matched case-insensitively,
so `01.welcome.zh-hans.md` works, but the canonical spelling is what gets
emitted.

Those files are **one article**: one permalink, one identity, one comment
thread. The version served at the bare `/pages/xxxxxx/` URL is the first
language in `:langs :priority` (`en → zh-Hans → zh-Hant → ms → ta`) that the
article actually has; the others are served under `/<lang>/pages/xxxxxx/`. An
article with **no English version** is entirely legal — it simply gets served in
whatever language it does have.

A near-miss suffix is a hard error rather than a silently-mistitled page:
`01.welcome.zh-CN.md` fails the build with "did you mean `zh-Hans`?", because
`zh-CN` is not one of the configured codes. Directories are never
language-suffixed.

### One trap: hyphenated slugs that look like language tags

The check that catches `zh-CN` recognizes anything shaped like a language tag —
**two or three letters, a hyphen, then more** — so a perfectly ordinary
filename can be rejected as a misspelled language:

| Filename | Result |
|---|---|
| `02.api-design.md` | **error** — `api-design` read as a language tag |
| `03.my-notes.md` | **error** — `my-notes` read as a language tag |
| `05.re-frame.md` | **error** — `re-frame` read as a language tag |
| `04.getting-started.md` | fine — `getting` is longer than three letters |
| `06.slug-cases.md` | fine — same reason |

The failure is loud and the message names the file, so nothing ships broken —
but it is surprising the first time. Three ways out, any of which works:

- **Reword** so the first hyphenated word is four letters or more:
  `03.designing-apis.md`.
- **Say the language explicitly**: `02.api-design.en.md` parses as the English
  version of *api-design*, and is the right answer when you want to keep the
  slug.
- **Use dots instead of the hyphen**: `02.api.design.md` is titled `api.design`.

To translate the **home page**, add `content/index.zh-Hans.md`. To translate the
theme's own chrome ("Previous", "On this page", …), see `i18n/README.md` —
that is a different mechanism and it is optional.

## Front matter, and what fills itself in

Write as little as you like. A new article needs nothing but a body; a `title:`
is worth adding because it is what readers see.

```markdown
---
title: Welcome
---

# Welcome
```

The generator **adds the missing keys and writes them back into the file**, in
this order: `title`, `date`, `permalink`, `categories`, `tags`.

```markdown
---
title: Welcome
date: "2026-09-06 03:20:41"
permalink: /pages/a1b2c3/
categories:
  - Notes
tags: []
---
```

Three rules govern this, and they are worth trusting:

1. **It only ever adds.** A value you wrote is never overwritten, in any key.
2. **It never reserializes the block.** New lines are inserted before the
   closing `---`; every byte you wrote stays exactly as you wrote it.
3. **It is idempotent.** Running it again on a normalized file produces no
   change at all.

EDN front matter (`{:title "Welcome"}` between the fences) is accepted too, and
is filled in the same surgical way. What is *not* accepted is a `---` fence at
the very top of a file wrapping something that is not a mapping — a stray
horizontal rule at the top of a document is read as front matter and fails the
build with an explanatory error.

### Permalinks are the article's identity

`permalink: /pages/a1b2c3/` is where the article lives, and it is deliberately
**not derived from the path**. Move the file, rename it, refile it under a
different category — the URL does not change, because the permalink travels
inside the file. That is the whole reason permalinks exist, and it is also what
keeps a comment thread attached to one article across all five of its
languages: every language variant inherits the permalink of its siblings rather
than minting a new one.

Two consequences:

- **Never edit or delete a `permalink:` that has been published.** You are
  changing the URL and breaking every link to it.
- **Never copy a file that already has one.** Two files with the same permalink
  and the same language is a collision. Delete the `permalink:` line from the
  copy and let it be assigned a new one.

`permalinks.edn` is a committed **ledger** of every permalink in the site plus a
tombstone register of retired ones. It is generated — do not hand-edit it — and
it exists so that collisions are detectable site-wide and so a read-only build
produces the same URLs as a normal one. Identity still lives in the files
themselves; the ledger is an auxiliary.

### CI will add permalinks to files you edit on the web

When you commit Markdown through the GitHub web UI, no local tool runs, so the
new file arrives with no `permalink`, no `date` and no `categories`. The publish
workflow's first step is `fm-fix`, which fills them in and pushes the result
back to `main` as:

```
chore: auto front matter [clogem-normalize]
```

So after editing on the web, expect a second commit from `github-actions[bot]`
touching the file you just edited. That is normal and it is the mechanism, not a
glitch. **Pull before your next local edit**, or you will be working on a stale
copy.

That commit does not trigger another build: it carries the `[clogem-normalize]`
marker, which the workflow's job-level `if:` refuses to re-process, and pushes
made with `GITHUB_TOKEN` do not start new workflow runs anyway. The build then
runs against the normalized tree it just produced, so even if the push fails
the published site is still correct and the repository catches up on the next
run.

One wrinkle worth knowing: the `date:` that auto-fill writes comes from the
file's **creation time on the machine that runs it**. On a CI runner every file
was created when the repo was cloned, so a file first normalized by CI is
stamped with the time of that checkout, not with when you wrote it — and
because auto-fill never overwrites, that value then sticks. If the date
matters, write `date:` yourself:

```markdown
---
title: Something
date: "2026-09-05 09:00:00"
---
```

Editing locally? Run the generator once before you commit and the write-back
happens on your machine instead, with no bot commit at all — and the date is
your file's real creation time.

## Working locally

The generator is not vendored here. Clone it beside this repository at the ref
`publish.yml` pins, and run it from this directory:

```sh
git clone https://github.com/EchoJustus/clogem-press ../clogem-press
cd ../clogem-press && git checkout d3b6f1792e0537f524b29838547444481f119c32 && cd -

bb --config ../clogem-press/bb.edn doctor          # report problems, build nothing
bb --config ../clogem-press/bb.edn fm-fix          # fill in front matter, write it back
bb --config ../clogem-press/bb.edn build --out /tmp/dist
bb --config ../clogem-press/bb.edn serve --dir /tmp/dist
bb --config ../clogem-press/bb.edn dev             # build, serve, rebuild on change
```

`bb --config … build --no-write` is a read-only build: it touches no source
file and takes its URLs from `permalinks.edn`.

Babashka is the only prerequisite (<https://github.com/babashka/babashka#installation>);
the generator resolves no dependencies of its own.

Build into `/tmp` or another directory outside the repository. Nothing generated
belongs in git.

## Publishing

Pushing to `main` under any of `content/`, `assets/`, `i18n/`, `overrides/`,
`site.edn`, `permalinks.edn`, or the workflow file runs
`.github/workflows/publish.yml`, which normalizes front matter, builds the site,
checks it is under the 500 MB budget, and deploys it to GitHub Pages. It can
also be run by hand from the Actions tab (`workflow_dispatch`).

The generator version is pinned by the `ref:` in that workflow, and that is the
**only** place the version lives. Bumping it is a one-line change; `site.edn`
deliberately carries no ref.

## What the pinned generator does not do yet

`clogem-press` is at `0.1.0-phase1`. The site it builds today is real and
correct, but several things `site.edn` accepts are documented intent rather
than working features. Knowing which is which saves you debugging something
that was never wired up:

| Not implemented at the pinned ref | Consequence |
|---|---|
| Category, tag and archive index pages | `:content {:category true :tag true :archive true}` is inert; there is no `/categories/` page to link to. |
| `sitemap.xml`, Atom feeds, `<link rel="canonical">`, hreflang alternates in `<head>` | `:seo` is inert. `hreflang` still appears as an attribute on language-switcher links. |
| Pagefind search, giscus comments, analytics | The three `:provider :none` settings are the only ones that do anything. |
| `overrides/` | The directory is a build trigger but nothing reads it. |
| `@pages/` generation | Files placed there are silently ignored. |
| Sidebar tree, TOC bar, `::: tip` containers | The sidebar is flat; `:theme :sidebar-open` is inert. |
| A language switcher on article pages | The switcher is emitted only when the article has more than one language version. On a single-language site it appears on the five home pages and nowhere else. |

**One of these is worth real caution.** Problems in `site.edn` — a violated
`:generator :min-version` floor, a `:langs :default` that names no configured
locale, an invalid `:giscus` value — are reported as errors on the console but
**do not fail the build**. The site is published and the job exits 0, and
`bb doctor` likewise prints the error and still reports "0 error(s)". Content
errors (a duplicate sidebar number, an unknown language suffix, front matter
that is not a mapping) *do* fail correctly. So after changing `site.edn`, read
the workflow log rather than trusting the green tick.
